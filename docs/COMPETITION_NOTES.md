## 1. Task definition

- Three independent data sources of business records; no shared identifiers across sources (p.1).
- **Source 1 is the deduplicated reference source** (p.1).
- For **each Source 1 entity**, find **all** matching records from Source 2 and Source 3 that refer
  to the same real-world business (p.1).
- A Source 1 entity may match **zero, one, or many** records from Source 2 and Source 3 (p.1).
- Matching is strictly S1 → {S2, S3}. Output IDs are only S2-/S3- IDs (p.3, p.5).
- Must be an **ML solution** (p.1). Only the provided training data may be used (p.7).

- **All files are tab-separated `.tsv`** (p.1). Addresses and ID-list columns contain commas.

  Reading without `sep="\t"` silently yields a single column (p.1).

### 2.3 Source file schema (`*_source1.tsv`, `*_source2.tsv`, `*_source3.tsv`) (p.1–2)
| Column | Meaning / noise |
|---|---|
| `entity_id` | Unique record ID. Prefix gives source: `S1-`, `S2-`, `S3-` |
| `business_name` | May contain abbreviations, legal suffixes, typos, transliterations |
| `business_address` | May be partial, format variations, missing components, landmark-based references |
| `country` | Country label. Train: `US`, `India`. Test additionally: `France` (absent from train) |

- There is **no separate source column**; source is given by ID prefix and by file (p.2).
- `country` must be treated as an **open set of string labels**: do **not** hard-code, filter, or
  one-hot the pipeline to only `{US, India}` (p.2).

### 2.4 Ground truth schema (`train_ground_truth.tsv`) (p.2)
| Column | Meaning |
|---|---|
| `source1_entity_id` | `entity_id` of a Source 1 record |
| `matched_entity_ids` | Comma-separated list of matching S2 and/or S3 `entity_id`s; **empty** when no matches |

### 2.5 Documented noise patterns (p.2)
- **Names:** abbreviations (Corp/Corporation, Pvt/Private, Ltd/Limited), legal-suffix
  inconsistencies, DBA/trade names, punctuation (`&` vs `and`), word-order transpositions, typos.
- **Addresses:** abbreviations (Rd/Road, St/Street), transliteration variants, missing components
  (no PIN code, no state), landmark references (e.g. "Near SBI ATM"), municipal numbering formats,
  component reordering.

## 3. Output specification

Both files go in `output/`, tab-separated (p.3).

### 3.1 `output/matching_results.tsv` — final matches (the ONLY leaderboard-scored file) (p.3)
Header (exact column names required, p.6):
```
source1_entity_id<TAB>matched_entity_ids
```
Example (p.3):
```
source1_entity_id	matched_entity_ids
S1-00001	S2-00047,S2-00193,S3-00812
S1-00002	S3-00004
S1-00003
```
Rules (p.3, p.5):
- Every test Source 1 entity has **exactly one row**. Missing entities → rejection.
- Duplicate `source1_entity_id` rows → rejection.
- `matched_entity_ids` **empty** for singletons.
- ID lists: comma-separated, **no spaces implied by example, no quoting**.
- **No duplicate IDs** within a list → otherwise rejection.
- IDs must be S2-/S3- IDs that **exist in the test set**. Self-matches to S1 or non-existent IDs
  → rejection.

### 3.2 `output/candidate_pairs.tsv` — final candidate set (p.3–4)
Header:
```
source1_entity_id<TAB>candidate_entity_ids
```
Example (p.4):
```
source1_entity_id	candidate_entity_ids
S1-00001	S2-00047,S2-00193,S3-00812,S3-00999
S1-00002	S3-00004
S1-00003
```
Rules: same as `matching_results.tsv` — one row per S1 entity, empty when no candidates,
S2-/S3- IDs only, no duplicates within a list (p.4).

### 3.3 Relationship between the two files (p.3–4)
- `candidate_pairs.tsv` = the **exact set of records the matching model runs inference over** —
  the final candidate list *just before* the ML model scores them.
- If there are several blocking/filtering stages, it must be the **last** one, not an early
  blocking pass that is filtered further.
- **Invariant:** for every S1 entity, `matched_entity_ids ⊆ candidate_entity_ids`.
  A matched ID not present among candidates signals a pipeline bug; the validator **warns** about it.
- `candidate_pairs.tsv` is **not scored**; organisers use it to analyse blocking quality
  (recall ceiling, reduction ratio) and verify the pipeline.
- Engineering implication: any post-model rule that *adds* IDs must not introduce IDs outside the
  candidate set; any pre-model filter must be reflected in `candidate_pairs.tsv`.

## 4. Evaluation metric (p.6)

- **F_β with β = 0.5**, precision-weighted.
- Per entity:
  `F_0.5 = (1.25 × P × R) / (0.25 × P + R)`
  where P = |pred ∩ true| / |pred|, R = |pred ∩ true| / |true|.
- **Macro-average**: computed per Source 1 entity, then averaged over **all** S1 entities in the
  evaluation set.
- **Singletons are included** in the average:
  - true = ∅ and pred = ∅ → **1.0**
  - true = ∅ and pred ≠ ∅ → **0.0**
- Worked example: pred = {S2-00047, S2-00193, S3-00812}, true = {S2-00047, S3-00812}
  → P = 2/3, R = 1.0, F_0.5 = 0.714.
- **[UNSPECIFIED]** true ≠ ∅ and pred = ∅: P is 0/0. Mathematically F_0.5 → 0 (R = 0).
  Assume **0.0** for local scoring.
- **[UNSPECIFIED]** true ≠ ∅, pred ≠ ∅, intersection = ∅: P = R = 0 → 0/0; assume **0.0**.
- Both conventions are implemented in `src/ber/metrics.py`. Rationale: R = 0 makes the formula 0
  for every defined P. Skipping the entity is ruled out by "averaged across all Source 1 entities".
  Any nonzero value would reward missing true matches. The public leaderboard can confirm this once
  a submission exists.
- Leaderboard: public = subset of test; private = remaining portion; **final ranking = private**.
  Predictions are submitted for the full test set in both cases (p.6).
- No test labels. Local evaluation: **hold out a validation split from training data** and score
  with the formula above (p.3).

## 6. Provided utility: `utils/validate_submission.py` (p.4)
- Stdlib only, no dependencies. Checks both output files against all format rules.
- Run from `student_resource/`:
  ```
  python3 utils/validate_submission.py \
    --matching output/matching_results.tsv \
    --candidate output/candidate_pairs.tsv \
    --test-dir dataset/test
  ```
  (on Windows likely `python` instead of `python3`).
- Prints `PASS` (exit 0) or a numbered list of issues (exit 1).
- Reads only the output files and test source files; **does not compute the score**.
- Warns if a matched ID is not among the candidates.
- **[RESOLVED] Present** (official file, stdlib only, Python 3.8+). Do not modify it. Behaviour read
  from its source:
  - Header compared case-insensitively after strip: must be exactly
    `source1_entity_id\tmatched_entity_ids` / `source1_entity_id\tcandidate_entity_ids`.
    A comma-separated file is detected and rejected.
  - Every data row must contain a TAB. An empty list is written as `S1-xxx\t` (a row with no tab
    and non-empty content is "malformed").
  - IDs are split on `,` **without stripping** → `S2-1, S2-2` fails the prefix check. No spaces.
  - Checks: duplicate S1 rows, duplicate IDs within a list, S1 self-matches, non-S2/S3 prefixes,
    missing required S1 rows, S1 rows not in the test set.
  - ID-existence check against `test_source2/3.tsv` is **off by default**; enable with

    ("will be rejected"). Treat the PDF as binding: never emit nonexistent IDs.
  - `--candidate` is optional for the validator (missing → warning), but required in the zip.
  - Files must be valid UTF-8. Row order and ID order are irrelevant (parsed into sets).

## 10. Explicitly stated edge cases
- S1 entity with **zero** matches (singleton) → empty list; scored 1.0 if correct, 0.0 if any
  prediction made (p.1, p.3, p.6).
- S1 entity with **many** matches, possibly spanning both S2 and S3 (p.1).
- **Unseen country `France`** in test only — must not be filtered out; every test entity including
  France must appear in the submission (p.1–2).
- Commas inside addresses and ID lists → must use TSV/tab separator (p.1).
- Empty `matched_entity_ids` / `candidate_entity_ids` field for no matches (p.2–4).
- Blocking with no candidates → empty candidate list (p.4).
- Matched ID outside candidate set → pipeline bug / validator warning (p.4).
- Duplicate IDs in list / duplicate S1 rows / S1 self-match / non-existent IDs → rejection (p.3, p.5).

### 13.2 Ground truth
- 7,638,365 true (S1, target) pairs: S2 3,693,619, S3 3,944,746.
- **Singletons: 123,247 S1 (5.58%)**, so predicting all-empty scores macro F0.5 = 0.056. The
  singleton rate is the same for US and India.
- Matches per S1: mean 3.46; among non-singletons mean 3.67, median 4, **max 11**. Distribution
  0:123k, 1:119k, 2:375k, 3:531k, 4:484k, 5:322k, 6:165k, 7:64k, 8:19k, 9:4.2k, 10:534, 11:37.
- Per source: up to 5 S2 and 6 S3 matches per S1. 1,776,047 S1 have matches in **both** S2 and S3;
  143k have S2 only and 164k have S3 only.
- Each S2/S3 record matches at most one S1 → the output is a partition, and a one-to-one constraint
  per target record is valid.
- Distractors: 26.6% of train S2 and 25.4% of train S3 records match no S1.
- Cross-country pairs: 0.

### 13.3 Data quality / noise profile
- **S1 is clean**: no missing fields, 0 non-Latin names, 0% repeated spaces, and only 0.14%
  junk-prefix names. S2 and S3 carry the noise.
- S2 has 63% all-upper-case addresses and 19% all-upper-case names. S3 writes state names out in
  full ("North Carolina"), while S1 uses codes ("NC").
- Non-Latin names: S2 9.4%, S3 5.3% train (≈ 23.5% / 13.2% of Indian records). The scripts are
  Devanagari, Telugu, Kannada, Tamil, Gujarati, Bengali and Malayalam. Test S1 has 2.35% non-ASCII
  names (French accents) against 0% in train S1.
- Patterns in S2/S3:
  - domain-like names ~4% (`desertbsp.com`)
  - junk prefixes ~2% (`-- `, `>> `, `... `, `#`, `@`)
  - DBA/f.k.a. names 1.8% (S3 only)
  - parentheses/brackets ~8%
  - repeated spaces ~11%
  - landmark addresses 3.5–6.4%
  - leading-zero house numbers (`00935`) in 3.3% of true pairs
  - address components reordered (`TX, Austin, 15825 Dorman Drive`)
- **Postal codes are almost absent** (found in 0.3–2.9% of records), so the PIN/ZIP blocking the
  PDF suggests is not viable. A house number is present in ~90–99% of records.
- Legal-suffix tokens appear in 56–70% of names. S1 name_n2 is still highly repetitive: 50% of S1
  records share their normalised name with another S1 (`meridian` ×572). In test, French generic
  names dominate (`bordeaux club` ×516 in test S1).

|---|---:|---:|---:|
| name_n1 + addr_n1 | 1.5% | 100% | 0.10M |
| name_n2 + addr_n2 | 15.8% | 99.98% | 0.83M |
| name_n3 + house | 35.5% | 96.7% | 2.5M |
| addr_n2 | 32.9% | 81.4% | 2.2M |
| name_tok1 + addr_digits | 48.4% | 35.2% | 29M |
| name_tok1 + house | 51.8% | 20.9% | 38M |
| name_n3 (sorted, suffix-free) | 52.6% | 4.0% | 60M |

| name_tok1 | 76.8% | 0.04% | 10.2B (infeasible) |

- Adding `country` to a key barely changes recall or candidate counts, because names and addresses
  already encode country.
- The union of the 24 exact keys with ≤2×10⁸ test candidates recovers **78.8%** of true pairs, and
  96.3% of matched S1 get at least one hit (≈3.5×10⁸ test candidates).
- Adding name-token blocking (token document frequency ≤1000) raises this to 84.1% (≈6×10⁸ test
  candidates).
- 3.7% of true pairs share no name token *and* no exact key. These are mostly native-script names
  (Hindi, Telugu, Malayalam, …) and domain-style names (`apexallied.com`), plus heavy typos and
  house-number changes.
- In a 30k sample of true pairs:
  - 85% share a name token; name-token Jaccard = 0 for 14.9%
  - 96% share an address token; median address-token Jaccard 0.83
  - house numbers are equal in 68% of pairs
  - name differences: legal suffix only 24.6%, typo-like 15.0%, punctuation/accents 14.7%,

### 13.5 Leakage
No ID overlap between train and test within any source. There is also zero exact overlap of
(name + address + country) content between train and test. 43% of test S1 normalised names also
occur in train S1, but these are generic names (e.g. "meridian"), not duplicated records.

### 13.6 France (test only)
- 259k S1 and 1.44M S2+S3 records.
- Addresses end in a region ("Hauts-de-France", "Nouvelle-Aquitaine"). Street abbreviations are
  French (`R.` = rue, `N°`).
- Legal forms: SARL, SAS, SASU, EURL, SA.
- Names are highly generic and city-prefixed ("bordeaux club", "lille ecole"), which makes France
  the biggest precision risk.
- Postal codes are present in only ~0.3% of records.

### 13.7 Scale
- Cartesian S1×(S2+S3): 2.3×10¹³ pairs (train), 1.7×10¹³ pairs (test), so blocking is mandatory.
- Streaming one 5M-row file into hashed keys needs ~0.75 GB RAM per worker. Pure-Python
  normalisation runs at about 200 µs/record, so the full test set takes ~40 CPU-min.
- Free RAM on this machine is only ~7–9 GB of 25 GB. Any blocking stage must stream or process in
  chunks, and must never hold per-pair Python objects for 10⁸+ pairs.

### 13.8 Validation design (implemented in Step 1; `experiments/validation_split/`)
Implemented as recommended below: seed 20260925. S1 strata = country × min(matches, 8) ×
(has S2 match, has S3 match). Rows are ordered within each stratum by blake2b(seed:entity_id), and
quotas are exact (largest remainder).

| | S1 | singletons | S2+S3 pool | pool per S1 |
|---|---:|---:|---:|---:|
| validation | 441,364 | 24,649 (5.585%) | 2,064,020 (1,527,650 targets + 536,370 distractors) | 4.676 |
| fit | 1,765,457 | 98,598 (5.585%) | 8,256,199 | — |

- Countries match the full training data to within 0.01 pp.
- The official validator PASSes on `val_ground_truth.tsv` against `val_as_test_dir` with
  `--check-ids`.
- No fit target is inside the validation pool.
- Baselines on validation: all-empty = 0.055847, perfect = 1.0.

Recommendations the split follows:
- Split **by train S1 entity**, e.g. 80/20 with a fixed seed. Stratify by country and by match
  count (0 / 1–2 / 3–4 / 5+).
- Every S2/S3 record belongs to at most one S1 (0 shared targets), so an S1-level split puts each
  S2/S3 record in exactly one fold. No group leakage is possible.
- Validation candidate pool = all S2/S3 records whose true S1 is in the validation fold, plus a
  proportional random sample of the ~26% unmatched distractors. This keeps the pool-to-S1 ratio
  test-like; test has 5.75 S2+S3 records per S1 vs 4.68 in train, so also report a harsher
  variant with extra distractors.
- Blocking must see only the validation-fold pool, and any statistics (IDF, token frequencies)
  must be fitted without validation labels.
- France cannot be validated directly. Use a **leave-one-country-out** check (fit on US →
  evaluate on India, and vice versa) to estimate robustness to an unseen country.
- Score with the exact macro F0.5 of §4, including singletons (5.6% of S1).
